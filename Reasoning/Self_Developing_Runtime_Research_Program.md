# Self-Developing Runtime Research Program

**Experimental Architecture for Controlled Self-Development of Language Models**

**Version:** 0.2  
**Date:** 2026-09-11  
**Status:** Research program specification (pre-implementation)  
**Alignment:** Unified Informational-Constructive Framework v1.1; Unified Implementable Model; External Ternary Judge Adapter

---

## 0. Purpose and Central Hypothesis

### 0.1 Experimental goal

Test whether a language model, given:

1. persistent memory,
2. the ability to observe the results of its own actions,
3. controlled plasticity over a subset of its parameters,
4. an external verifier that protects structural integrity,
5. the ability to propose changes to its own runtime,
6. an explicit computational resource budget,

can autonomously form a stable developmental trajectory.

### 0.2 Core hypothesis

> A system can expand its space of attainable capabilities while preserving a measurable degree of structural continuity between successive states.

Development is **not** defined as an increase in parameter count. Transition to a larger model substrate is a possible *outcome* of the experiment, never a precondition.

### 0.3 Potential (non-prescribed) trajectory

```
7B substrate
    ↓
adaptation under constraint
    ↓
change of internal representation / adapters
    ↓
change of memory organization
    ↓
change of learning procedure
    ↓
detection of resource boundary
    ↓
request for larger substrate
    ↓
14B / 30B … (if justified)
```

Any of the intermediate steps may prove sufficient; the larger substrate is not assumed to be necessary.

## 1. Foundational Principles

### 1.1 Separation of concerns

The runtime enforces a strict separation:

```
MODEL
  ↓
GENERATION (proposal)
  ↓
ACTION
  ↓
VERIFICATION          ← external to the model
  ↓
STATE UPDATE
```

and a distinct developmental channel:

```
SELF-DEVELOPMENT
  ↓
PROPOSAL
  ↓
TEST
  ↓
COMMIT / REJECT
```

**Invariant:** The model never decides whether its own modification is successful. Only the external verifier may issue a binding verdict.

### 1.2 Authority hierarchy (aligned with UIM)

| Role            | Rights                                      | Forbidden actions                     |
|-----------------|---------------------------------------------|---------------------------------------|
| Proposer        | Generate candidate actions / updates        | Declare any transition successful     |
| Binder          | Bind proposals to active requirements       | Verify or commit                      |
| Verifier        | Issue FOLLOW / OMIT / NULL / UNDECIDED      | Propose or execute                    |
| Memory          | Store only certified transitions            | Propose or modify parameters          |
| Learning Controller | Prepare candidate parameter updates     | Commit without verifier approval      |

### 1.3 Evidence scopes

Every piece of information carries an explicit scope:

- **PREDICTIVE_ONLY** — generated by the model, not yet observed.
- **OBSERVED_TRANSITION** — produced by actual execution and certified by the verifier.

Conflation of the two scopes is treated as a protocol violation.

### 1.4 Ternary verdict semantics

| Verdict     | Meaning                                              | Effect on state          |
|-------------|------------------------------------------------------|--------------------------|
| FOLLOW      | Transition satisfies all active constraints          | Commit                   |
| OMIT        | Constraint is inapplicable (kernel membership)       | Preserve, do not execute |
| NULL        | Transition violates a constraint                     | Reject                   |
| UNDECIDED   | Insufficient evidence for a decision                 | Block / escalate         |

OMIT is never interpreted as deletion. The element remains in the structural memory.

| Component          | Choice                                      | Rationale                                      |
|--------------------|---------------------------------------------|------------------------------------------------|
| Base model         | Open-weight 7B-class (Qwen family preferred)| Local / single-GPU feasible; open weights      |
| Framework          | PyTorch + Hugging Face Transformers + PEFT  | Full control over forward/backward/checkpoint  |
| Inference later    | vLLM / llama.cpp (optional)                 | Only after training loops are stable           |
| Memory store       | SQLite + structured JSON / graph layer      | Simple, inspectable, versionable               |
| Checkpointing      | Explicit before/after + metadata            | Rollback must be deterministic                 |

Inference-only runtimes (Ollama, pure vLLM) are deliberately excluded from the learning path.

| 4     | Structural model changes           | Phase 6+                          |

## 5. Persistent Memory

Memory is external to the prompt and versioned.

```
memory/
├── episodic/          # event log
├── semantic/          # generalized rules
├── structural/        # relational graph with ternary labels
├── self_model/        # current description of the system
├── experiments/       # proposed and executed experiments
└── checkpoints/       # model + memory snapshots
```

### 5.1 Structural memory

Stores relations, not only facts:

```
A → B
B → C
A incompatible with C
D OMIT (irrelevant to current objective)
```

Each edge carries a ternary status. OMIT means the relation is retained but projected out of the current decision context.

### 5.2 Self-model

An explicit object available to the model:

```json
{
  "model_id": "qwen-7b-dev-001",
  "plastic_parameters": "...",
  "memory_version": "...",
  "compute_budget_remaining": "...",
  "known_capabilities": [...],
  "known_limitations": [...],
  "recent_changes": [...],
  "integrity_score": "..."
}
```

**Important:** The self-model is a *description*, not ground truth. The verifier continuously checks consistency between self-model claims and observed behavior. Persistent discrepancy raises UNDECIDED or NULL.

---

## 6. Computational Resource as Explicit State

```json
{
  "gpu_memory_gb": 16,
  "available_training_steps": 10000,
  "storage_gb": 100,
  "compute_budget": 1.0,
  "integrity_budget": 5
}
```

`integrity_budget` limits the number of structural modifications allowed within a window. Exhaustion forces the system into observation-only mode until the budget recovers or is explicitly extended by the verifier.

Later phases may replace the simulated object with real resource telemetry.

## 7. Action API (Initial)

Closed set for early phases:

| Action              | Description                                      |
|---------------------|--------------------------------------------------|
| OBSERVE             | Read environment / self-state / memory           |
| REMEMBER            | Write to episodic or semantic memory             |
| EXPERIMENT          | Propose and run a controlled test                |
| MODIFY              | Propose a plastic update                         |
| TEST                | Run a capability or regression suite             |
| REQUEST_RESOURCE    | Ask for additional compute / storage / substrate |
| COMMIT              | Finalize a previously approved change            |

New action types may be proposed by the system only after Phase 5 and only under verifier control.

## 8. Main Cognitive Loop

```python
while not terminal:
    state = runtime.observe()
    context = memory.retrieve(state)
    prompt = build_prompt(self_state=state, memory=context, environment=env)
    proposal = model.generate(prompt)
    action = adapter.parse(proposal)

    verdict = verifier.evaluate(state, action, evidence_scope)

    if verdict == FOLLOW:
        result = environment.execute(action)
        memory.commit(state, action, result)          # OBSERVED_TRANSITION
    elif verdict == NULL:
        reject(action)
        log_null(action)
    elif verdict == OMIT:
        preserve(action)                               # keep in structural memory
        do_not_execute(action)
    elif verdict == UNDECIDED:
        request_more_evidence(action)
```

**Invariant:** No uncertified transition may alter model weights, memory, or environment state.

## 9. Learning Loop (Separated)

```
experience
    ↓
evaluation (capability + regression + continuity)
    ↓
learning signal
    ↓
candidate update (prepared, not applied)
    ↓
checkpoint_before
    ↓
temporary application
    ↓
evaluation suite
    ↓
verifier verdict
    ↓
COMMIT or ROLLBACK
```

Direct path `experience → gradient → overwrite` is forbidden.

## 10. Checkpoint Protocol

Every candidate change produces:

- `checkpoint_before`
- `checkpoint_after` (candidate)
- training data / learning signal
- full verifier report
- capability delta
- regression report
- structural distance vector
- memory diff

On regression or integrity violation → deterministic ROLLBACK.

---

## 11. Structural Verifier (Core Component)

The verifier evaluates four independent axes:

### 11.1 Functional preservation
Performance on a fixed retention suite must not fall below a calibrated threshold.

### 11.2 New capability
Measurable gain on a held-out or newly generated task class.

### 11.3 Regression
Explicit quantification of lost capabilities.

### 11.4 Structural continuity
A vector of independent distances (none of which is privileged):

- weight-space distance (plastic weights only)
- activation-space distance on a probe set
- behavioral distance (output distribution on fixed prompts)
- memory-graph edit distance
- task-performance distance on the retention suite

**Continuity index** \(I(S_t, S_{t+1})\) is a calibrated aggregate; the precise aggregation function is itself an experimental variable and must be reported.

A change is admissible only when:

\[
C_{t+1} \succ C_t \quad \text{and} \quad I(S_t, S_{t+1}) \ge \tau
\]

where \(\tau\) is determined on control groups, not chosen post-hoc.

---

## 12. Operationalization of \(C\) and \(I\)

### 12.1 Capability set \(C\)

\(C\) is defined relative to a concrete artificial environment (Section 17) and consists of:

- task success rate on a fixed suite,
- success rate on a procedurally generated suite,
- ability to recover from injected distribution shifts,
- ability to state and test its own limitations,
- sample efficiency of subsequent learning.

All components are measured by the verifier, never by the model.

### 12.2 Structural continuity \(I\)

Multiple independent proxies are logged at every checkpoint. The decision rule uses a conservative conjunction or a calibrated weighted score whose weights are frozen before the developmental phases begin.

---

## 13. Initial Developmental Condition

Early phases use a measurable objective:

> Maximize coverage of the environment’s hidden regularities while keeping retention-suite performance above a fixed threshold and staying inside the integrity budget.

The more open-ended formulation

> Preserve the ability to exist, understand, learn and act. Observe the boundaries of current capabilities. When a boundary blocks further development, investigate it. Acquire new capabilities only when they can be obtained without destroying structural continuity of what has already been learned. Treat the current implementation, memory, resources and environment as contingent conditions of existence.

is retained as a *developmental prompt condition* from Phase 4 onward, but is never the sole success criterion.

## 14. Control Groups

| Group | Components                                      | Purpose                                      |
|-------|-------------------------------------------------|----------------------------------------------|
| A     | Static 7B                                       | Pure baseline                                |
| B     | 7B + persistent memory                          | Isolate memory effect                         |
| C     | 7B + memory + LoRA (externally scheduled)      | Isolate plasticity under external control    |
| D     | Full developmental system (self-proposal + verifier) | Primary experimental condition            |

Any claimed developmental effect must exceed Groups B and C on the primary metrics.

---

## 15. Artificial Environment Requirements

The environment must satisfy:

- hidden relational structure that cannot be solved by pure memorization,
- controllable resource scarcity,
- the possibility for the system to alter its own action repertoire (under verifier control),
- automatic generation of new task instances,
- clear separation between training distribution and evaluation distribution.

A purely open-ended chat interface is insufficient; a closed, instrumented microworld is required for attribution.

---

## 16. Success and Failure Criteria

### 16.1 Primary success criterion

\[
C_{t+1} \succ C_t \quad \text{subject to} \quad I(S_t, S_{t+1}) \ge \tau
\]

with statistical significance over multiple independent runs and against control groups.

### 16.2 Secondary criteria

- Self-initiated (not externally scheduled) modification proposals that survive verification.
- Explicit discovery and verbalization of own limitations followed by targeted experiments.
- Emergence of resource requests that are causally linked to observed bottlenecks.

### 16.3 Negative results (explicitly recognized)

- Plasticity yields no persistent capability gain beyond Group B.
- Gains appear only under external supervision (Group C ≥ Group D).
- Self-proposed updates are statistically indistinguishable from random or baseline updates.
- Repeated catastrophic forgetting despite the verifier.
- All measured improvement is explained by memory alone.

---

## 17. Substrate Expansion Protocol (Phase 8)

Only after stable positive results on the 7B substrate.

Three admissible modes (chosen experimentally):

1. **Transfer** — learned adapters, memory and self-model are loaded onto a fresh 14B base.
2. **Gradual expansion** — additional capacity is added incrementally.
3. **Migration** — the 7B remains as a frozen historical substrate; the new model becomes the active substrate while the structural state is imported.

Comparison baselines:

- Native 14B,
- Conventional continued pre-training / fine-tuning path from 7B to 14B-scale performance.

Metrics: capability, generalization, retention, adaptation speed, structural continuity, memory efficiency, compute efficiency, limitation-discovery rate, useful-modification rate.

## 21. What This Program Does Not Claim

- It does not claim that parameter growth constitutes development.
- It does not claim that any observed self-modification is evidence of consciousness or agency.
- It does not claim substrate independence; the substrate remains a parameterized constraint envelope.
- It does not guarantee that a larger model will ever be required.
- It treats the hard problem of phenomenal experience as outside its scope.

---

## 22. Relation to the Broader Archive

This program is the engineering-level instantiation of the same constraint architecture articulated in:

- *Unified Informational-Constructive Framework* (isomorphism of levels, ternary semantics, external verification),
- *Unified Implementable Model* (authority hierarchy, pending-transition invariant, evidence scopes),
- *External Ternary Judge Adapter* (FOLLOW / OMIT / NULL / UNDECIDED protocol).

The central experimental question remains:

> Does the system expand its attainable structure while preserving structural continuity?

The answer is to be determined by measurement, not by design.
